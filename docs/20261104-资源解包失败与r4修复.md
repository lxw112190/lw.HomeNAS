# 资源解包失败与r4修复

## 原因

现有APK的ClientMaintenance.stageUi只接受html/css/js/png/jpg/jpeg/webp/svg/woff2/json。我们之前生成的资源包含licenses/APACHE-2.0.txt、MIT.txt、NOTICE.txt，签名和下载摘要通过后，会在遍历ZIP时抛出“资源文件路径或类型无效”。因此r3无法通过既有APK解包，界面保持builtin。以前只验证签名、ZIP CRC、HTTP发布下载和模拟页面，漏查了真实消费者的解包类型规则。

这属于资源包兼容缺陷，不能通过反复下载或改服务器端口解决；修改未来APK的白名单也无法修复已安装的APK。本次不修改APK、不放宽原生文件校验。

## 修复和使用

许可证全文包裹为转义后的HTML，保留版权说明与完整条款；索引链接改为.html，符合已分发APK白名单。新包使用递增revision=4、minNative=1，签名身份不变。简约界面设计沿用r3。

在Web“存储与设置”的安卓资源发布表单中，选择本轮 `ui-r4.zip` 和配套 `release.json`，点击上传并发布资源。不要再发布旧r3，也不要把APK构建Artifact当成资源ZIP。

手机旧界面点“检查更新 → 下载资源更新”。提示下载完成后，从最近任务中划掉应用再重新打开，确保新的Activity读取已暂存资源。无需清除数据或卸载APK；保留原队列、登录和相册授权。新界面可从“我 → 软件更新”查看资源版本，应显示r4。实际激活仍需手机复测。

使用完整部署包时，停止NAS，更新client-release和deploy，保留原config/data，运行deploy/import_android.bat，再启动服务。脚本导入的资源变为r4，默认仍是CI5原始APK。

## 防止再次发生

新增tools/android_ui_policy.py，打包前及CI源检查都验证每个文件的路径/类型、重复名称、文件数量、展开大小和必要入口。测试核对该白名单与Java源码实际正则一致；不可签名后才发现当前APK不接受。打包工具拒绝直接覆盖已有同revision资源，已发布内容使用更高revision修复。

本轮14项Host CI测试通过，包含不允许TXT、许可证链接、重复/越界路径与大小/数量限制。许可证转换前后全文逐字比较一致。

使用本机已有JDK编译运行从ClientMaintenance.stageUi原样提取的解包循环：旧r3稳定复现拒绝，新r4完整通过。这是桌面JVM验证，不等同Android真机激活测试；没有安装Android SDK或生成新APK。

r4签名及全部资源摘要校验通过；隔离NAS验证上传摘要、发布清单、公开下载字节一致及匿名发布拒绝。诊断ZIP原件未复制进源码或部署包，也未修改用户NAS服务或公网服务器。
