# Windows CI依赖哈希不一致修复

首次完整包工作流在 `tools/check-dependencies.py` 报 `third_party/httplib/httplib.h` 哈希不一致，尚未进入发布步骤，没有公开不完整包。

已逐个核对284个依赖：Git中原始blob、开发目录内容均与 `third_party/dependencies.lock.json` 完全一致。使用 `git -c core.autocrlf=true cat-file --filters` 可复现Windows检出后的改写：

| httplib.h | SHA256 |
| --- | --- |
| 原始文件与锁定值 | `805169049e6a6e9ba7729d7e01d14ced825029c88a277586602a6b38df4d5357` |
| 修复前Windows检出过滤结果 | `036fb07d4616b2c261211a5c64014c037936bdbf043d78e4f37c2adf2306e049` |
| 修复后同一过滤器结果 | 与原始锁定值一致 |

原因是Windows自动把LF转换为CRLF。新增 `.gitattributes` 的 `third_party/** -text`，让Git按原始字节保存和检出这些依赖，不修改上游文件、不更换锁定哈希、不忽略换行差异。

校验错误现在打印期望与实际哈希，若符合纯CRLF转换则给出定位提示，但仍失败。新增3项回归：所有284个锁定文件均禁用文本转换、四套依赖的代表文件通过Windows Git过滤后哈希正确、换行改写或真实内容修改均不能绕过校验。

将 `.gitattributes` 加入Android CI的main推送触发路径。本轮提交推送后会重新构建Android，再自动接续同一新提交的Windows完整包和发布流程。仅重跑旧提交仍会使用旧检出规则；不能把新源码和旧APK混装发布。

本机原始字节审计和回归已通过；修复后的云端完整发布需本轮推送后验证。本次只改Git检出规则、校验诊断与CI测试，APK功能和版本保持0.7.0-dev/code10。

## 补充：FFmpeg许可证也必须保护

随后CI通过了284个C/C++依赖校验，但在 `COPYING.GPLv3.txt` 停止。上一轮遗漏了 `tools/ffmpeg/provenance.json` 锁定的文本：GPLv3全文、ImageIO许可和二进制README。三份文件的Git原始blob均匹配既有pin，Windows检出转换后均不匹配。

新增 `tools/ffmpeg/** -text`，同时保留原有 `third_party/** -text`。回归现在合并两份清单，检查全部287个已跟踪锁定文件的Git属性，并通过Git Windows检出过滤器验证四套源码代表文件及上述全部三份FFmpeg文本的原始哈希。EXE和源码压缩包由下载步骤独立校验，不作为源码提交。

FFmpeg校验增加期望/实际大小和哈希、CRLF提示，仍严格拒绝改写内容。发布脚本把Git属性与发布单测提前至FFmpeg下载前，尽早发现检出规则遗漏。本机284源码校验、FFmpeg完整性校验、9项Python发布回归（内含20项Node模拟发布检查）均通过；修复后的云端运行仍待推送。
